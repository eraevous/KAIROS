Telosmith preview · the demo

The tests passed. What did the change put in doubt?

A one-line change to a discount function passes the checks that existed for it. Telosmith reads the reasons recorded next to the code and names the requirement the change touched, plus the claim and the decision built on that requirement, so a person knows what to re-check.

Everything below is real output from Telosmith's own demo, examples/without-spec-kit, run on 23 November 2026 on Linux. The full transcript has every line. (aec is Telosmith's command-line tool; the command kept its earlier name.)

1. The project and its records

A tiny shop package. Next to the code, a records file says what the shop is for and what has been decided. Each record links to the one it rests on:

  1. Purpose P0, version 2 provisional · not yet accepted

    A tiny shop whose checkout never charges a negative amount.

  2. Requirement R-1 committed · accepted

    Discounts never make a price negative. Why: refunds are separate negative line items (anchored to docs/pricing.md, lines 3–4).

  3. Code

    shop.pricing.apply_discount and the clamp it calls.

  4. Claim C-1 candidate · not yet accepted

    Checkout totals are never negative. Depends on R-1.

  5. Evidence E-1

    apply_discount(10, 150) returned 0.0 by hand. Supports C-1.

  6. Decision D-1 accepted by the owner

    Ship the checkout with the never-negative guarantee. Depends on C-1.

The owner in this example is a fictional "Ada". In the demo's records, "committed" and "accepted" mean the owner has signed off; "provisional" and "candidate" mean proposed, not yet accepted.

2. The change

On a feature branch, one line of shop/pricing.py changes:

def apply_discount(price, pct):
-    return clamp(price * (1 - pct / 100))
+    return clamp(price * (1 - pct / 100.0))

3. The ordinary check passes

The example ships no test suite, so we turned its recorded evidence E-1 into a two-line check and ran it before and after the change:

from shop.pricing import apply_discount
assert apply_discount(10, 150) == 0.0
assert apply_discount(10, 20) == 8.0
--- before the change
ok: apply_discount(10, 150) -> 0.0 ; apply_discount(10, 20) -> 8.0
--- after the change (pct / 100 -> pct / 100.0)
ok: apply_discount(10, 150) -> 0.0 ; apply_discount(10, 20) -> 8.0

4. What Telosmith reports

The same commit, through the pre-commit hook. Telosmith compares the code's structure before and after, finds that apply_discount changed, and follows the records outward:

# derived 1 change event(s) from the structural diff
# aec impact

- change: revise code:shop.pricing.apply_discount (by code, authorized_by None)

[stale] R-1@1: Discounts never make a price negative.
    via code:shop.pricing.apply_discount -> R-1@1
[needs_review] C-1@1: Checkout totals are never negative.
    via code:shop.pricing.apply_discount -> R-1@1 -> C-1@1
[needs_review] D-1@1: Ship the checkout with the never-negative guarantee.
    via code:shop.pricing.apply_discount -> R-1@1 -> C-1@1 -> D-1@1

3 affected, 2 conclusions with no status change
  • stale: the code a requirement names has changed since the requirement was last checked against it.
  • needs_review: a claim or decision rests, through the links shown, on something that is now stale.
  • The hook reports by default and the commit goes through. With TELOSMITH_BLOCK=1 the same report blocks the commit. The demo also runs the pre-push hook and a CI step with the same result.

A flag calls for review. It does not say the requirement was broken. Here it wasn't: in Python 3, pct / 100 and pct / 100.0 give the same result, and the check above still passes. Telosmith's findings are structural: it knows which conclusions depend on the changed code, not whether they still hold. Deciding that is the developer's job.

5. What to inspect next

  1. Re-read R-1 against the new code. Does apply_discount still never return a negative price? Its rationale is anchored to docs/pricing.md, lines 3–4.
  2. Re-run the evidence. E-1 was a hand check. Repeat it, or replace it with a real test.
  3. Record what you found, without editing old lines. The records file is append-only: add a new version of the evidence (or of R-1, if the requirement itself should change). The demo's append-only guard refuses an edited line.
  4. Leave the decision to its owner. D-1 was accepted by the owner. Whether it still stands is the owner's call, with your new evidence in front of them.

The demo shows two quieter cases too. Editing clamp, which apply_discount calls, gives a pointer (a candidate for attention, no status change). Editing the LIMIT constant, two hops away, gives nothing at the default depth.

Run it yourself

You need Python 3.10 or newer, git and bash. Telosmith uses only the standard library. The run takes about five seconds; after the clone it needs no network.

git clone https://github.com/eraevous/Telosmith.git
cd Telosmith
git checkout 98bbab5792f70a7913b170f5ab745037a38678ef
PYTHONPATH=src bash examples/without-spec-kit/run.sh

You should see [stale] R-1@1 and [needs_review] lines for C-1 and D-1 under == pre-commit, blocking mode, and the script should exit 0. To remove it, delete the Telosmith folder; the demo writes only to a temporary folder.

What has been measured

In its first controlled test, Probe-001, giving coding agents Telosmith's briefing did not improve their results, and it did not lower their cost. Read its scope before generalising: 18 trials, three tasks on one repository, one AI model, and tasks a capable agent could solve with plain search. What the demo shows is what Telosmith reports, not that reporting it makes development better.
