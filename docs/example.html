Worked example

One requirement, traced from purpose to tests

Telosmith's aec append refuses to write a record that aec check would reject. A newcomer asks: where did that rule come from, and what shows the code actually follows it?

Nobody has to remember. The answer is a chain of records in the repository, each one linked to the next. Everything below is copied from Telosmith's own records file, which Telosmith keeps about itself; ids are exact, wording is shortened. (aec is Telosmith's command-line tool; the command kept its earlier name.)

How to read the labels: committed means the owner has accepted the record; provisional and candidate mean an agent proposed it and the owner has not yet accepted it.

The chain

  1. Purpose AEC-P0, version 3 committed · accepted by the owner

    Telosmith helps people and AI agents build and evolve tools while preserving why those tools exist and what they must accomplish.

  2. Requirement AEC-R-adoption provisional · not yet accepted

    Adopting Telosmith in another repository needs no hand-hashing and no hand-editing. aec append adds a record with computed anchors, refusing duplicates and records that check would reject.

    Why: the requirement is anchored, by a content hash, to the owner's decision record DEC-095 (an ADR-style entry) in his private ledger, cited by id. You can't open that ledger, but anyone who has it can check that the hash matches the passage cited. It serves the purpose above.

  3. Code implemented_by

    src.aec.init.init, src.aec.append.build, src.aec.append.make_anchor: the functions the requirement names as its implementation.

  4. Claim CL-R-adoption candidate · not yet accepted

    That code behaves as the requirement states, including refusing without writing anything.

  5. Evidence EV-R-adoption-tests candidate · not yet accepted

    tests/test_adoption_friction.py, written before the change: 22 tests, 19 of which failed until the code existed. One of them is test_record_that_check_rejects_is_refused.

When it changed, the old reason stayed visible

  • Version 2: the requirement grew. It added a named CI workflow and an aec anchor command. The claim and the evidence were not edited: each got a new version that supersedes the old one, and the tests grew to 30, the new ones again failing first.
  • Version 3: the purpose changed. When the owner adopted a new purpose text (DEC-116), the requirement and its claim were re-pinned to it, each with a one-line rationale saying the requirement's own text did not change.

What this buys you

  • Answers from the record, not from memory. Why a behaviour exists, which code carries it and what shows it works are each one link away, for a person or an agent.
  • Change without erasure. Every earlier version is still in the file; a reviewer can see what a requirement used to say and why it moved.
  • Honest labels. The requirement is provisional and the claim and evidence are candidates: proposed by agents, not yet accepted by the owner. The records say so.

This shows how the records are kept. It is not evidence that keeping them makes development faster or better; the findings and the draft paper Measuring whether coordination helps are about that open question.
