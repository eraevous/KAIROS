Kairos: keeping the reason attached to the work

Status: preliminary draft, agent-drafted from the project records on 2026-11-06; the owner has not yet reviewed or endorsed this text.

Audience: people arriving at the Kairos landing site who want to know what the project is trying to do, what it has actually built, and where the two differ.

The problem

Current AI tools let one person do work that used to need a team. In Kairos that person is the owner, and the team is a changing set of coding agents from more than one model family, plus a second-family reviewer (a ChatGPT thread the records call Kate). The work moves fast. What does not keep up is the record of why anything was done.

The failure mode is specific. A decision is made in a chat, acted on in a repository, and summarized in a handoff. A week later a fresh agent reads the summary and treats a proposal as a permission, or a historical statement as a current fact. The project's own external review (November 5, 2026) put it this way: "prose describes authority and changes more richly than the software can resolve them. Agents then fill the gap by interpreting summaries, sometimes mistaking a recorded statement for a verified fact or a current permission."

So the problem Kairos works on is not "make agents write more code." It is: when one person coordinates many agents, keep the decisions, the reasons, and the objections attached to the work, in records a stranger can audit later, and then find out whether doing so actually helps.

Three ideas that recur

The front-door README names three ideas that appear in every repository. They are stated here with the records that gave rise to them.

1. The reason stays attached to the thing

Purposes, requirements, claims, decisions and objections are records that link to code and to each other, and they are append-only. A line is never rewritten; a correction is a new line that supersedes the old one. CI in the public repositories refuses rewrites.

The portfolio synthesis of November 5 describes the whole project as "one idea built eight times: keep the reason for a thing attached to the thing, in an append-only record a stranger can audit later." It also notes, as inference, that this is the owner's audit-and-compliance background turned into software.

2. Information crosses freely; authority never crosses implicitly

This is DEC-019 (adopted October 31, 2026): "information crosses freely; authority never crosses implicitly." Agents read everything and may propose anything. Only the owner accepts a decision or merges a pull request. A message relayed from another model is a proposal, never an instruction. Every substantive PR gets a fresh-context review and a review from a different model family before merge (DEC-038, adopted November 3), and the agents do not merge.

The records show why the rule exists. The feedback-taxonomy pass of November 6 catalogs a loop it calls "Cockpit batch adoption" (L19): the owner accepted a batch of items in one sentence, and the coordinator wrote seven decisions and nine challenges within an hour, several with a one-word basis. The reviewers read this as cheaper adoption lowering the quality of recorded reasoning; the owner's recorded position is that it was not a problem. The disagreement sits in the ledger, unresolved. The system does not settle it on the owner's behalf.

3. Count and ask; never fabricate meaning

Every claim carries how it was established: measured, inferred, or declared. Tools refuse to compute what the data cannot support, and they ask the human for domain meaning rather than inventing it.

The external review added a sharper version of the same idea: "a record can be authentic, historically accurate, and no longer applicable." The README now lists this among the project's recurring principles.

How the ideas show up in each tool

Telosmith

Telosmith keeps recorded reasons attached to code. Records (purposes, requirements, claims, evidence) link to code symbols; check validates the record set and code-impact reports which written requirements, claims and decisions a code change endangers, marking them stale or needs_review. It is plain Python with no third-party dependencies, at version 0.5.0 on main with the release tag pending, and the README cites more than 300 tests.

Two cold-user evaluations (November 4 and November 6; see Paper 2 for the method) found the core loop working: a fresh agent with no build context installed it, wrote records against a toy project, edited the linked function, and saw the written requirement and its claim come back verbatim in under a second. The same evaluations also found that the documentation promised more than the default hook delivers. Editing a helper two call-hops away from an annotated function produces nothing by default; one hop produces a pointer by record ID rather than the text. The evaluator's proposed honest pitch, recorded as an inference: "edit the linked function → the written requirement and its claim come back verbatim; one hop → a pointer by ID; two hops → a note, silent in the hook."

relay-kit and the Cockpit

relay-kit is the coordination kit: handoffs with ids and states, append-only decision and challenge ledgers, chat capture and cross-model relay, a read-only export, a static Cockpit page generated from the records, and a read-only MCP server. The private records repository is where the ledgers live; the Cockpit is generated from them, never hand-edited.

This is where idea 2 is enforced mechanically. A handoff carries an "Authorized" section that must quote the owner's words; the handoff tool refuses to send one with that section unfilled. Decisions carry a decider, a basis and a locator pointing at where the words were said.

It is also where the limits are most visible. The external review reproduced six synthetic cases in which a merely proposed decision claiming to supersede another removed the target from the Cockpit's view, and showed that budget restrictions, their tightening and their later relaxation were all projected as "in force" at once, because the software has no amendment or expiry semantics. A shared lifecycle resolver is the proposed fix and is in flight. Two decisions of November 6 (DEC-139, DEC-140) redirect the Cockpit toward decision support: PR review text and a daily coordinator narrative rendered verbatim, with no AI summarizing in the page; and for each pending choice, authored notes on what changes if it is accepted, what does not, the counterfactual, whether it can wait, and what depends on it. Two notes per item, one from the coordinator and one from the second-family reviewer, labeled and append-only.

Fathom

Fathom produces deterministic, offline data-review reports: a data dictionary, structure findings with the threshold printed beside each verdict, time-series and panel structure, and a "liftoff" brief that asks what the data cannot tell you. Reruns are byte-identical, and the tests run with every network socket blocked.

Idea 3 is Fathom's whole design. The third cold-user run (November 5) confirmed that when a series had only five weekly periods, the tool reported "insufficient … ACF/PACF not computed" rather than computing a meaningless autocorrelation, and that each printed verdict reproduced exactly in pandas. The same run also found the idea unevenly applied: a borough with a $10 lower mean fare was reported as "no marked contrast" because the gap fell below the printed threshold, but the threshold was shown far from the verdict, so a reader would conclude the tool was wrong; and amplitude statistics were still printed for a one-month series that the tool had elsewhere declared not estimable. The evaluator's summary: correct, but the gate is too far from the verdict.

QAT-Kits

QAT-Kits packages cognitive tools (StressTest, TruthWeight, FrameShift, NegativeSpace, ThreadMap, MetaDistill and others) as contract-checked specifications that can be chained and evaluated. The aim, in the README's words, is for "a model to think in a named way rather than ramble." Here idea 1 appears as a contract: the tool's purpose and output shape are written down and checked, rather than left to a prompt.

The honest state is thin. Typed specs exist for two tools; the rest are prose. There is no canonical copy, and the contributing guidance explicitly says not to declare one. The synthesis lists it as a spike.

The Commander deck-analysis repository (MtG) is the first Telosmith pilot outside Telosmith itself: the same records approach applied to a hobby decision, with a pinned card knowledge base as domain truth that agents cite and never decide.

The guiding light

On November 5, 2026 the owner adopted an official guiding purpose for the project (DEC-127): "We are building Cognitive Augmentation." The phrase originated as a line in the second-family reviewer's round 14 ("Stop optimizing Kairos primarily for development throughput. Start optimizing it for Zach's capacity to realize intentions"), and the owner's recorded reply was: "We can optimize Telosmith and RelayKit for development, but the entire project is Cognitive Augmentation."

The same decision defers the definition. In the owner's words, the forthcoming papers and articles "will be where I define and declare Cognitive Augmentation." Until then no agent writes a definition into a purpose file, and this paper does not attempt one. The only operational reading the records permit is the one the README states: every build is judged by whether it increases a person's capacity to realize their intentions.

A related decision (DEC-134, November 6) names the engineering principles the owner wants applied across the code: parsimony, elegance, and modularity, which he glosses as "things that can be taken in or put back."

What is built, and what is claimed

It is worth being exact about the gap, because the project's own records are exact about it.

Built and exercised by someone with no build context:

  • Telosmith's record validation, typo suggestions, and direct-link impact report.
  • Fathom's two-stage flow, byte-identical reruns, offline operation, refusal to compute on short series, and threshold-gated contrasts.
  • relay-kit's handoff state machine, append-only ledgers, static Cockpit, and read-only MCP server.
  • Fresh-context and two-family review as a working practice, with blocking findings recorded before merges.

Claimed in prose but not yet demonstrated, per the records:

  • That Telosmith's records have told an agent something the files did not. DEC-093 made a "second demonstrated use" the condition for wider rollout; the taxonomy pass of November 6 reports that no record shows one.
  • That the Cockpit saves the owner time or errors relative to the plain status.py script. DEC-093 set that acceptance test; it had not been run when the Cockpit was widened.
  • That the governed build process produces better software. The one comparative experiment so far (fathom-002) scored it below two simpler approaches on first-build quality; Paper 2 reports this in full.
  • That QAT-Kits is a toolkit rather than a collection of prompts with two typed specs.

Inference, labeled as such: the project's most distinctive asset at this point is not any one tool but the record of its own operation, failures included. Whether that habit yields a tool other people want is the open question, and the subject of the second paper.
